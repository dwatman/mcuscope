- **D1**: apply the `+` de-optimisation the codebase already uses for `port` - `+cf.can_id IN (...)` - so the driver stays the `cf.line_id` primary-key scan and `LIMIT` stops it early; measured 133 ms to **2.21 ms** on the same statement. ## Ruled out, with the evidence

- **`until_ts` / `since_ts` inclusivity.** `until_ts` is inclusive and `since_ts` exclusive, exactly as SPEC 833 says, and the API result is **identical to direct SQL** on both ends (`drive_daemon.py bounds`). `since_ts == until_ts` is an empty 200 by construction, an inverted window is a 400 on all four endpoints.
- **Ties in `_window_id_ceiling`.** A burst of rows sharing one `ts` (routine on Windows, where `time.time()` ticks at 15.625 ms) does *not* truncate: the plan is `SEARCH lines USING COVERING INDEX idx_lines_ts`, and a descending walk of `(ts, rowid)` yields the highest rowid of the tied group. Driven with 50 rows at one `ts`: ceiling 50, all 50 selected. Only a backwards clock step breaks it (D6).
- **Non-finite floats reaching a CSV or a deadband.** They cannot be stored: `parse_plot_value` rejects `nan`/`inf` spellings *and* re-checks `math.isfinite` after the float conversion (protocol.py:673), and the typed `!ps` decoder does the same at protocol.py:845 and 890. Worth recording what would happen if one ever did: `_changed` computes `abs(nan - prev) > band`, which is `False`, so a **deadband would silently hide a NaN excursion** that plain `changes` shows (driven through `_changes_long`: ids `[1, 3]` with a band, `[1, 2, 3]` without). Unreachable today; it becomes a defect the moment a non-finite value can be stored.
- **Bytes that are not UTF-8 in `raw`.** `serial_link.py:771` decodes with `("ascii", "replace")`, so `raw` holds U+FFFD and never a lone surrogate; no `.encode()` in the export path can raise mid-stream.
- **Class 2, newlines.** The diff uses no `csv` module (so its `\r\n` default is not in play) - every CSV is hand-rolled with an explicit `"\n"`. The zip members are written through `zf.open(arcname, "w")`, which is binary, fed `chunk.encode()`; `writestr` likewise. StreamingResponse encodes UTF-8 with no translation. Driven: no `\r\n` anywhere in a text, jsonl, csv or `lines.txt` body.
- **Chunk boundaries splitting a row.** `_chunked` accumulates whole rendered lines and joins them, so a split can only fall on a line boundary, in `str` space, before the encode.
- **Class 49, a streamed export left partial.** My first drive read this as a defect (a catastrophic `match=` returned 200 with an empty body and no error) and it was **wrong**: those patterns simply matched nothing, and `/lines` answered the same way in the same time. Re-driven by injecting a real `MatchBudgetExceeded` into page 2 over a **real uvicorn socket** (`probe_budget_midstream.py`): the client raises `RemoteProtocolError: peer closed connection without sending complete message body (incomplete chunked read)`. The docstring's claim holds. The daemon writes no file for these exports, and the one file it does write (the bundle temp) is unlinked on `BaseException`.
- **A client disconnecting mid-stream.** Six aborted `/lines/export` downloads against the 1M-line capture left the daemon's fd count unchanged at 11; the private read connection is released by the generator's `finally` when it is collected.
- **The db copied while the WAL has pages.** There is no file copy: `export_session_db` `ATTACH`es the live capture and runs `INSERT ... SELECT` per table on its own connection, so SQLite resolves the WAL for it and no checkpoint is owed. Driven: a **closed** session's bundle gives `capture.db` 23584 lines = `lines.txt` 23584 = direct SQL 23584, exactly.
- **Class 44, a relative bound re-evaluated per page.** `last_ms` is anchored through `_window_floor(last_ms, id_to)`, and both `/lines/export` and `/can/frames?format=csv` freeze `id_to = store.max_id()` before the first page, so every page resolves the same floor. `/plot/export` and the bundle freeze `id_to`/`hi` once for every store call. Complies (the filename is the exception, D3).
- **Empty and degenerate windows.** An empty `/lines/export` is a 200 with nothing (`text`, `jsonl`) or the header alone (`csv`), as SPEC 717 requires; an empty CAN csv keeps its header; an empty session's bundle is a valid 1985-byte zip of `capture.db`, `lines.txt` and `manifest.json` with no plot or can members.
- **A malformed CAN id list.** `zz`, `0x100,zz`, `-1`, a trailing comma and `0xFFFFFFFF` are each a 400 naming that element. A 400-element list is a 200; the parameter count cannot reach SQLite's `SQLITE_MAX_VARIABLE_NUMBER` (32766 here) because the HTTP layer refuses the URL first.
- **A `plot_<sid>.csv` name collision with `plot_adhoc.csv`.** `sid` is exactly one ASCII digit (`protocol.py:_parse_plot_def_tokens` refuses anything else), so the member names are `plot_0.csv` .. `plot_9.csv` and cannot collide.
- **`chan=` on the export.** An invalid channel is a 422 from the `Chan` enum, the same as `/lines`, not a silently empty export.

Throwaway daemon, 1,054,065 lines / 1,094,761 plot points / 261,315 CAN frames, `GET /status` polled in a tight loop from a second thread throughout.

**Worst observed loop stall: 42.9 ms**, no request errors in any run. The 47.0 s row is D1, and it is a worker cost rather than a loop cost - the loop stayed under 34 ms throughout it.

## The two questions

**Q1, least confident, re-driven.** My first reading of class 49 said `/lines/export` answers a catastrophic `match=` with a 200 and an empty body, indistinguishable from an empty window. I had driven three patterns that each returned 200 with 0 bytes - but `/lines` returned an empty result for the same patterns in the same time, so the budget had never fired and I was reading "nothing matched" as "silently truncated". Re-driven by injecting a real `MatchBudgetExceeded` into page 2 and reading the stream over a **real uvicorn socket** rather than the TestClient: the client gets `RemoteProtocolError ... incomplete chunked read`. Claim withdrawn; the docstring is right. Second-least confident: D6's reachability. The mechanism is driven and exact, but it needs a backwards wall-clock step, which I did not produce on a live daemon - I injected the rows. Filed as LOW for that reason, and the report says so rather than counting it as a live defect.

**Q2, the gap nobody looked at.** Two.

- **The in-memory branch of the new exports** (`store.py:2328`, `2334`). `open_lines_export` and `open_can_export` materialize the *entire* selection into a list on the event loop when `db_path` is `:memory:`, and the old `MAX_EXPORT_ROWS` cap that used to bound exactly that is gone from this diff. The removed cap's justification ("a cap can only truncate a response whose headers have already gone out") is about the streaming path; it does not argue for an unbounded materialization on the loop. No test in the repo drives either endpoint against an in-memory store, so nobody has seen how long that blocks. `--sim` demos and the test harness are the configurations that hit it.
- **A retention sweep or a purge landing inside a bundle build.** `bundle_session` freezes `hi` and then awaits six times before `asyncio.to_thread(build)`, which itself runs for seconds on a real session. Nothing holds `_sweep_lock` across that, so a size sweep or a `POST /purge` can delete rows out of `[lo, hi]` while the members are being drained - and the members are drained at different times, so they would disagree with each other *and* with the manifest, silently. D2 is the same disagreement arriving by a different route, which is what made me look; the purge route is untested and unmentioned anywhere in the diff.
